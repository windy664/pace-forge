# pace-forge

**运动世界校园 非官方客户端** — 纯 Rust，一条命令完成登录、轨迹生成与提交。

> 针对 **7.4.21** 实测（脱壳 dex 逐字段核对过，7.4.20 → 7.4.21 协议零变化）。
> CLI + Web 双模式，不用装 App、不用模拟点击、不用真机跑。
> 版本号是硬编码的，厂商换版本需要重新对齐（见「已知局限」）。

> ⚠️ 本项目涉及第三方应用私有协议的逆向实现，运行结果会直接落到你的账号上。使用前请阅读[免责声明](#免责声明)与[使用者的义务](#使用者的义务)。

```bash
pace-forge run 2 12      # 跑 2 公里 / 12 分钟，直接提交
pace-forge web           # 或者开网页，点一下就跑
```

---

## 两种跑法

| | 记分跑（校园跑） | 户外跑（自由跑） |
|---|---|---|
| 报文 `sportType` | `1` | **`4`** |
| 策略 `runMode` | `1` | `2` |
| 时段 | **有固定时段**，不在时段内报 `11016` | 无限制 |
| 打卡点 | 必须全过（`fivePointJson` 带点位） | 无（报文**省略** `fivePointJson`） |
| 围栏 | 必须在校区内 | 不拉围栏 |
| 学期目标 | 有（`semesterDis` / `selDistance`） | 不计入学期成绩 |

### 记分跑

计入体育课成绩的那种。生成前先查学期进度：

```bash
pace-forge semester        # 看还差多少公里 / 几次
pace-forge run 2 12        # 在有效时段内提交
```

`selDistance` 用的是**规则给的最小里程**，不是你自己设的目标——填错会被驳回。

### 户外跑

不计学期成绩，但**轨迹和步数照常记录**。省掉三个接口：策略里的时段检查、
围栏、打卡点（点位那个有 5 分钟 3 次的限流）。

```bash
pace-forge run-free 2 12        # 命令行：跑 2 公里 / 12 分钟，按户外跑提交
# 或者在网页「跑法」里选「户外跑」
```

报文形状与记分跑的区别：

- `sportType=4`
- **整个省略 `fivePointJson`**（不是发空串）。这个字段不进签名（31 字段表里没有它），
  移除不影响签名；OBS 明细的 `fixed_point_json` 仍发 envelope（内层空数组）
- 轨迹绕锚点自由生成，不做围栏内缩、不吸附打卡点

依据是 neko（NekoSportsWorldTool）的实测：`sportType=4` 是自由跑、`6` 是户外跑，
策略走 `runMode=2`（无时段限制、`geoFence=null`）；`2`/`5` 服务端拒「uid 不存在」，
`3` 有特殊的 `roomId` 签名规则。

## 它能做什么

| 步骤 | 说明 |
|---|---|
| ⓿ 查进度 | 学期累计里程 / 次数，知道还差多少 |
| ① 登录 | 极验 v4 全本地求解，不需要打码平台 |
| ② 拉策略 | `runModePolicy`，拿规则串和最小里程 |
| ③ 选围栏 | 多校区按定位锚点自动选对 |
| ④ 拉打卡点 | 必经点全部命中 |
| ⑤ 规划轨迹 | 闭环折线，凑到目标里程 |
| ⑥ 反推时间戳 | 由速度剖面算出每点时刻 |
| ⑦ 合成步数 | 步频 / 步幅 / 10 秒分桶 |
| ⑧ 自检 | 八类检查，不过就不发 |
| ⑨ 上传明细 | OBS 对象存储 |
| ⑩ 提交成绩 | `runnings/save/record` |

Web 界面默认 `:9999`（`pace-forge web 0.0.0.0:9999`）：登录、记录列表、轨迹地图、模式切换、自检结果实时显示。

## 为什么这个能过

市面上流通的实现大多只做到「报文能发出去」，数据本身经不起看。这三个问题是实测发现的：

### ① 步频、步数、速度三者打架

服务端拿 `totalSteps / totalTime` 和 `totalDis / totalTime` 一除，就能反推你声明的步频，跟配速对不上就驳回。

常见的 `150 + 12v` 公式在 6:40/km 会给出 180 步/分，真实数据只有 144——差 36 步，而且**形态是反的**：

| 配速 | 实测步频 | 正确公式 | 拍脑袋公式 |
|------|---------|---------|-----------|
| 5:31/km | 170 | 169 | 173 |
| 6:40/km | 144 | 146 | 180 |
| 7:02/km | 139 | 140 | 177 |
| 8:19/km | 125 | 124 | 162 |

慢配速时步频掉得更快，是**步幅主导**而不是步频主导。pace-forge 用的关系式由下面 4 组样本拟合得出：

> ⚠️ **样本量说明**：n=4 的一元线性回归只剩 2 个自由度，残差标准差和 R² 都没有统计意义。
> 这条公式是**基于 4 个点的拟合与推测**，不是经过验证的规律。它的价值在于「比常见的
> `150+12v` 形态正确」，而不在于精确。要当成结论用，需要补到 30 份以上真实记录。

```
步频(步/分) ≈ 34.4 + 44.5 × 速度(m/s)
```

并写成硬约束，误差 < 1e-9：

```
v = (cadence / 60) × stride
```

> ⚠️ **上表和 `evidence/` 里的真机记录口径不同，两个都对**：
> 两条真实记录的 App 汇总页是 `6'44"→90 步/分`、`6'08"→104 步/分`
> （见 [证据文档](evidence/real-device-app-summary.md)），比上表低 50 步上下。
> 原因是 App 那两个字段由「步数 ÷ 时长」「距离 ÷ 步数」派生，而手机计步器
> 会少计（手持/放包里），于是步频偏低、步幅偏大。上表是**步态**，真机汇总是
> **计步口径**。我们目前发的是步态（约 157 步/分 @ 5'47"），所以 `totalSteps`
> 会比真机记录高——这一处还没对齐，写在「已知偏差」里。

### ② 10 秒分桶是白噪声

`stepsPerTenSec` 如果用均匀随机数抖，相邻桶互相独立——一阶自相关 0.089，这是随机数的指纹。真人步频有惯性，自相关显著为正。

用 Ornstein-Uhlenbeck 过程做均值回归：

```
c_{t+1} = c_t + θ(target_t − c_t)·Δt + σ·√Δt·Z,   Z ~ N(0,1)
```

对比（`0.089` 是均匀随机生成器的理论值，`0.569` 来自少量真人记录的估算，样本不足以给出置信区间）：

| 方案 | 标准差 | 相邻差 | 一阶自相关 |
|---|---:|---:|---:|
| 均匀随机 | 3.36 | 3.66 | **0.089** ← 随机数指纹 |
| OU 均值回归 | 2.01 | 1.42 | **0.569** ← 真人量级 |

θ=0.07 对应相关时间约 14 秒，桶间隔 10 秒时相关性还有 0.5。

**这里的自相关是真的有测试守着的**：`lag1_autocorr()` 按标准定义算
`r1 = Σ(x[i]-μ)(x[i+1]-μ) / Σ(x[i]-μ)²`，测试要求生成结果高于白噪声上界 `2/√n`，
并用一条反向测试确认纯白噪声会被判为无相关。

### ③ 时间戳和速度对不上

如果点位等距、时间戳也等距，等于全程匀速；但报文里的 `speedPerTenSec` 有起伏，两者放在一起自相矛盾。

正确关系是 `dt_i = d_i / v_i`：速度快的段用时短。总时长用**最大余数法**分配，`Σdt` 从构造上精确等于目标，不存在累积舍入误差。

实测偏差：

```
剖面速度 vs 实测速度：平均 0.23%，最大 0.49%
分桶速度 vs 桶内实测：最大 0.00%
总时长误差：0 ms
```

## 速度剖面是物理的

不是恒定配速，也不是纯随机波动：

- **起跑热身**：前 20 秒从 0.85× 匀速 ramp 到 1.0×
- **中段起伏**：OU 均值回归
- **弯道预判**：`v² ≤ v_corner² + 2·b·d`，提前 40m 以 1.5 m/s² 收速
- **终点冲刺**：最后 150m 线性提速 12%

全程匀速跑完是最容易识别的机器特征之一。

> 关于弯道减速：400m 标准跑道内圈半径 36.8m，2.8 m/s 配速过弯的向心加速度只有 0.198 m/s²，远低于人体上限（约 2.5 m/s²）——**这个配速本来就不需要减速**。弯道限速只在速度 >4 m/s 或半径 <10m 的急弯实际生效。

## 两种路线模式

### 自由路线

在定位锚点周围生成闭环折线，自动凑到目标里程，必经打卡点全部穿过。

**起点和终点可以分开**（2026-11 加）。表单里那行「终点纬度 / 终点经度」留空时
仍然是闭环（跑完绕回起点）；填了、或点「在地图上点终点」，轨迹就变成：

```
起点 → 全部必经点（按顺序）→ 跑够目标里程 → 收在终点
```

里程控制上，`plan()` 先把「最后一点 → 终点」那一段预留出来，再让尾巴续走剩余
里程，最后把末点钉死在终点、里程对齐时锁住首尾两端——不然等距采样和
`scale_to_length` 都会把终点挪走（测试 `end_point_is_honored` 钉的就是这个）。

界面上的「手绘轨迹」也有配套提示：画多长、离目标还差多少、首尾没接上会不会被
判跳变，都在面板那行直接写出来。

### 操场绕圈

按 World Athletics 标准 400m 跑道建模：

```
        ┌──────────────────────┐
       ╱                        ╲
      │   直道 84.39m            │     弯道半径 36.50m
       ╲                        ╱      半圆长 115.61m
        └──────────────────────┘

  一圈 = 84.39×2 + 115.61×2 = 400.00m
```

支持 1–8 道（每道宽 1.22m）。实测：

| 道次 | 圈长 | 生成 5 圈 | 闭合误差 | 弯道曲率 |
|---|---:|---:|---:|---:|
| 第 1 道 | 400.0m | 1999.1m | 0.00m | 0.02719 |
| 第 2 道 | 407.7m | 2037.5m | 0.00m | 0.02632 |
| 第 4 道 | 423.0m | 2114.2m | 0.00m | — |

理论曲率 `1/36.8 = 0.02717`，实测 0.02719。直道曲率 0.00000。

## 提交前自检

**宁可本地失败，也不要把注定被驳回的报文发出去。** 驳回会记错误次数，异常多了触发风控，连正常提交都会被拦。

八类，分两级（致命先拦，警告只提示）：

| 检查项 | 等级 | 内容 |
|---|---|---|
| 时间轴 | 致命 | 起止戳缺失、顺序颠倒、跨度与 `totalTime` 不符 |
| 轨迹时间 | 致命 | 首末点没落在报文边界、时间戳非严格递增 |
| 里程 | 致命 | 折线实测与声明差 >2m |
| 坐标 | 致命 | 越界 / (0,0) / 相邻跳变 >200m |
| 打卡点 | 致命 | 任一必过点最近距离 >0.5m |
| 分桶 | 致命 | 桶数不符、步数和不等于总步数 |
| 上报节奏 | 致命 | 采样轴不是 5 秒等时间（出现 1~2 秒空洞即 `SAMPLE_RATE` / `SAMPLE_RATE_SHORT`）；配置偏离真机只报警告 |
| 物理 | 致命/警告 | 配速超规则区间、步频超人体范围、步幅异常、步态不匹配 |

```bash
pace-forge dry 2 12      # 只走自检，不发任何写请求
```

### 主体配速

自检里有一条**只提示、不拦**：主体配速。

起步窗口占时长但不产里程（`startup_sec` 秒里几乎不动），剩下的时间要把全部里程跑完，所以**真正发出去的逐点配速是主体配速，不是「距离/时长」那个平均值**，两者能差半分钟以上。

这个差别决定一条记录在 App 里看起来红不红。学校区间是 5'00"~10'00" 时：

| 距离/时长 | 平均 | 主体 | 结果 |
|---|---|---|---|
| 2km/12min | 6'00" | **5'04"** | 距下界只有 4 秒，逐点反复穿越 → 红蓝交替 |
| 2km/14min | 7'00" | 5'55" | 越界，整条红 |
| 2km/16min | 8'00" | 7'12" | 落在区间中央，基本全蓝 |

生成时会打印：

```
! [pace] 主体配速 5'04" 距区间边界只有 4 秒（区间 5'00"~10'00"）——正常的逐点波动就会越过边界标红，建议留出 1 分钟以上余量。
```

距离和时长是用户选的，主体配速是它们的数学结果，所以这里**只报警不改参数**。

## 提交台账（防重复记录）

提交请求发出去但**结果没回来**的情况只有三种：超时、连接被重置、响应体解析失败。这三种里服务端都可能已经入账了。此时再跑一次，服务端就会看到同一时间段的两条记录——那不是「配速偏快」这种能解释成跑者习惯的差异，而是**物理上不可能**：一个人不可能在同一段时间里跑两次。这是最容易被判定异常、也最难解释的形态。

所以台账记的是**意图**而不是结果：请求发出之前先落盘一条 `pending`，拿到 rrid 之后补 `accepted`，服务端明确驳回才补 `rejected`。

```bash
# 台账位置：~/.pace-forge/submissions/<uid>.jsonl
# 每行一个事件，O_APPEND 单次 write，多进程不会互相截断
```

三道拦截：

| 情况 | 行为 |
|---|---|
| **同一时间段**上次结果未知 | **拦住**，提示去运动记录页核对。「查不到」不等于「没入账」，不自动重试 |
| **别的时间段**上次结果未知 | 放行，另起一行提醒「另有某时段结果未知，建议核对」 |
| 该时间段已有本工具提交的记录 | 拦住，报出冲突的 rrid |
| 不同账号 | 各记各的文件，互不牵连 |

第一行和第二行的区别很关键：拦的依据只有「同一段时间不能跑两次」。一次超时把账号永久卡死，比放任一条待核对记录糟糕得多。

「明确驳回」才释放时间段：有业务错误码、能确定没入账的（`11016` 不在时段、`10003` 签名错误、`10603` 被限流等）。网络错误、HTTP 异常、响应看不懂一律**保留 pending**。

## 配置文件与环境变量

所有开关的优先级：**环境变量 `PACE_*` > `config.toml` > 内置默认值**。

```bash
pace-forge web --config /etc/pace-forge/config.toml   # 显式指定
# 不指定时依次找 ./config.toml 和 ~/.pace-forge/config.toml，都没有就全默认
```

- 全部键见仓库根的 `config.example.toml`（带注释）；当前哪些开关非默认、
  来自哪一层（env / config.toml），Web 启动日志会打一行「非默认开关」；
- 配置文件里的**未知键、非法值、缺一半的锚点**（`center_lat`/`center_lng`
  只写一个）都在启动时报错退出——不再静默回落默认值；
- 环境变量仍然全量支持（老用法不变），非法值同样启动报错；
- Web 启动时打一行「非默认开关」，谁改了什么一眼可见；
- 拆分实现在独立 crate `crates/pace-forge-config`：注册表一张表同时服务
  TOML 解析、env 解析、`config` 打表，不存在「文档表」和实际读取两套东西。

## 出口代理

人在外地、但有一条能回到学校同城的线路时，可以把提交链路走那条线路：

```bash
export PACE_EGRESS_PROXY=http://10.0.0.2:7890     # 只支持 http:// 的 CONNECT 代理
export PACE_FORGE_TOKEN=...
pace-forge web 0.0.0.0:9999
```

也可以写进 `config.toml`（`network.egress_proxy` / `server.token`），见上一节；
网页里保存的设置仍然优先于这两种来源。

- 只有**提交链路**走这个出口，探测归属地仍直连，所以顶栏那行显示的是「代理的出口」；
- 出口可以是本机直连、HTTP 代理，或自己搭的隧道；程序只负责把流量送过去；
- 换出口后提交立即走新的，但同一个进程只有一个出口生效；
- 没设就直连，行为和以前逐字节一致；值写错会打一行 `[egress]` 并按直连走（不静默）；
- 归属地是否与校区同城由 `audit` 提示，不同城只提示、不拦提交。

## 违规名单自查

提交成功不代表没被标记——很多判定是事后跑批判定的。服务端有 `POST /api/v78/cheat/cheatlist`，本项目把它接出来了：

```bash
pace-forge cheat          # 退出码：0 无记录 / 2 已标记 / 3 结果未知或过期
```

### 退出码

所有子命令统一按失败的类别退出，脚本按码分支，不要去解析中文报错：

| 码 | 含义 | 脚本一般怎么处理 |
|---|---|---|
| 0 | 成功 | — |
| 1 | 其它失败（本机环境、读写文件、JSON 解析） | 原样报给人看 |
| 2 | 参数用法错误 | 改命令 |
| 3 | 仅 `cheat`：结果未知或过期 | 见上一节 |
| 4 | 登录态无效或凭据缺失 | 先 `pace-forge login` / `relogin` |
| 5 | 触发频率限制 | 退避后再试 |
| 6 | 网络（连接、超时、DNS） | 稍后重试 |
| 7 | 厂商拒绝（带业务错误码） | 看 `error_code`，不要盲目重试 |
| 8 | 围栏/打卡点几何上规划不出轨迹 | 换围栏或目标里程 |

Web 界面走 `GET /api/cheat`。四种状态分得很清楚：

| 状态 | 含义 |
|---|---|
| `no_record` | 服务端明确返回 null 或 `count=0` |
| `flagged` | 服务端已标记，带原因、时间、申述状态、关联 rrid |
| `unknown` | **字段缺失或格式异常。不等于清白** |
| `stale` | 超过 5 分钟，请重新查 |

第二条是这套逻辑的重点：`self` 字段整个缺失、`count` 是字符串、`self` 是非对象——这些都算「未知」。把未知报成清白比不报更糟，用户会以为查过了没问题。

## 提交前四道闸门

`run` 真正发请求之前会先过这四关，任何一关不过都直接返回错误（不消耗提交）：

| 闸门 | 查什么 | 不通过时 |
|---|---|---|
| **违规名单** | `v78/cheat/cheatlist` 的 `self` | 已标记就停：继续提交只会往名单里再加一条 |
| **跑步冻结** | `policy.freezeRunTime` | 冻结期拒绝，并报剩余秒数（App 里开始按钮是倒计时的） |
| **日上限** | 今日累计 + 本次 > 服务端 `dayGoal`（实测某校 3000m） | 直接拦。`PACE_IGNORE_DAILY_LIMIT=1` 可硬跑 |
| **有效时段** | `getHistoryConfig` 的 `randomValidTimes` | 窗口外拒绝（服务端会回 11016） |

日上限从 `runRuleModel.dayGoal` 读（各模式一致，`runMode=1` 在有效时段内才给，所以读失败时用 `runMode=2` 兜一次），读不到才退回 5000。实测某校 `dayGoal=3000`，而 `getHistoryConfig` 的 `maleDayUpper` 还是 5000——以 `dayGoal` 为准，按记录逐日反算是 3000 封顶。
时段字段名就叫 `randomValidTimes`（不是笔误），实测某校是 `06:30:00 – 22:00:59`。

## 提交后回读服务端判定

提交成功只是「进账」，不代表「算成绩」。服务端把裁定结果写在记录详情里，
`run` 会立刻回读并逐条打印：

```
√ [submit] 提交成功，记录 id=Some(1375850386)
√ [obs] 3/3 个 key 上传成功
√ [verify] 服务端判定：status=0(正常) isCheat=0 stepFreqStatus=0 validDis=1824m/1824m
  · ✓ 经过必经点位
  · ✓ 至少通过2个普通点位
  · ✓ 最少要跑1.50公里
  · ✓ 跑12分钟以上
  · ✓ 步频控制在40步/分钟-300步/分钟之间
  · ✓ 配速控制在2′00″-12′00″
√ [verify] 这一条服务端认可：无作弊标记、无扣量、规则全达标
```

字段含义：

| 字段 | 说明 |
|---|---|
| `isCheat` | 作弊标志，0 = 干净 |
| `stepFreqStatus` | 步频判定，0 = 正常 |
| `status` | 记录分类：0 正常 / 1 作弊 / 2 未打卡 / 3 未上传 / 4 配速过快 / 5 步频过慢 |
| `validDis` / `validTime` | **服务端算的**有效距离/时间，和 `totalDis` 的差就是被扣掉的部分 |
| `reasonList` | 逐条规则的裁定，`complete=false` 的那条就是没过的 |

任一不正常会汇总成一条 `! [verify] 服务端有意见：…` 并给下一步动作。
只读，回读失败不影响已提交的记录。

**「经过必经点位」与「至少通过2个普通点位」是两条独立规则**：服务端把 `isFixed=1`
的点当必经点，其余当普通点，普通点只要过 2 个就算过。

## 客户端本地校验对齐

7.4.21 在客户端本地加了一层校验逻辑，本项目在提交前会用同一套规则先验证一遍，避免发出注定被拒的数据。

### 点位打分

7.4.01 新增的 `libswsport.so` 里有个 `isValidPoint`，**不是布尔判断，是打分**：

```
score = 基础分(点位等级) + 模式分 + 距离分 + 时间分
valid = (标志A == 0) && (标志B != 0) && (score > 65)
```

各项上限：基础 30、模式 30、距离 30、时间 10，满分 80。
要过 65 分，**基础分必须 ≥ 25**，也就是点位等级要够高——不是随便一个点都算数。

距离分的关键阈值是 **10 米**：相邻点间距低于 10 米才拿满分。

`pace-forge` 默认采样 5 米一个点，所以符合本地间距条件的相邻点占比 100%：

```
$ pace-forge check 2 12
=== 点位体检（模拟 7.4.01 本地规则）===
  点位检查通过 · 符合本地间距条件的相邻点占比 100.0% · 平均间距 5.0m（本地统计）
  判定: ✓ 通过
```

注意这个占比是**本地统计**：`pace-forge` 在你自己机器上按间距条件算的，
检查通过说明轨迹本身干净、像真跑；最终成绩怎么算，只由服务端审核和学校规则决定。

间距超过 10 米只扣分，超过 20 米直接拦截——因为那已经不是"跑步采样稀疏"，是"轨迹断了"。

### 心率字段

7.4.01 **移除了** `BODY_SENSORS` 权限，不再读心率。所以报文里如果还带心率，
反而是"用旧版本伪造"的信号。提交前会自动剔除：

```rust
pub const FORBIDDEN_FIELDS: &[&str] = &[
    "heartRate", "heartRates", "hrData",
    "avgHeartRate", "maxHeartRate", "bodySensors",
];
```

### 硬件指纹

7.4.01 的 Manifest 把这三个设成 `required=true`（不满足就装不上）：

```
android.hardware.sensor.stepcounter    计步器
android.hardware.sensor.stepdetector   步伐检测
android.hardware.bluetooth             蓝牙
```

前两个是步数来源，第三个对应新增的 `getBluetoothInfo`（穿戴设备同步）。
纯软件方案不带这些，属于"设备指纹不全"，但服务端目前没有强制校验的证据。

设备身份字段的口径，写在这里免得每个读代码的人都猜一遍：

- `cpuModel`：默认仍发 ABI（`arm64-v8a`）。要发 SoC 型号，设
  `PACE_DEVICE_MODEL=<机型或平台代号>`，程序查 `data/devices.json`：
  `platforms` 是平台代号 → SoC（`kalama` → `SM8550`，公开命名，已收 17 条），
  `models` 是机型 code → 平台代号（**每条必须有出处**，出处为空的不采信，
  当前为空表）。查不到就退回 ABI 并提示「未收录」——不编。
  补表方法：`bash tools/collect_device.sh`（真机 adb 一条命令，输出可直接粘进
  `models`），把 src 换成你的出处（截图/日期），`pace-forge devices` 可核对。
  为什么只收有出处的：没有真机佐证的映射就是编，编一个比留 ABI 更像真的假。

  网页里也能改：账号面板下面新增「设备机型」一节——搜 model code（`2211133C`）或
  机型名（`Xiaomi 13`），选中后填平台代号（`kalama`）保存，`cpuModel` 立刻生效。
  这份映射按账号落盘（`.pace-forge-device-model-<hash>`），机型→平台映射落在
  `<数据目录>/device_models.json`，**只影响本机，不进仓库**。改机型不动 `device_id`。

  另有一层**官方目录** `data/device_catalog.json`（Google Play 设备目录的中国品牌
  子集，4565 条 model code → codename / 营销名 / 品牌，抓取日期见文件内 `fetched`）。
  它只用来**认设备**：`PACE_DEVICE_MODEL=2211133C` 会显示「Xiaomi 13（fuxi）」，
  手填错了会提示「目录未命中」。目录里没有芯片字段，所以它**不参与** SoC 判定——
  从 codename 猜平台一样是编。重新生成：`python3 tools/import_play_catalog.py <csv>`。
- 三个 MAC 首字节都是本地管理位（`0x02`），语义是「虚拟网卡」，不借任何厂商
  OUI。借前缀只是更像的假，不是真的。
- IMEI 15 位、TAC 以 `86` 开头、末位 Luhn 校验，由 `device_id` 确定性派生，
  同一账号每次一致。
- `androidId`/`blMac`/`wifiMac`/`IMEI`/`CustomDeviceId` 这五个头**默认发空串**。
  依据是 7.4.21 的 `HttpUtil.getHeaderMap` 里它们本来就写死成 `""`：

  ```java
  arrayMap2.put("IMEI", "");
  arrayMap2.put("androidId", "");
  arrayMap2.put("blMac", "");
  arrayMap2.put("wifiMac", "");
  arrayMap2.put("CustomDeviceId", "");
  ```

  （`CustomDeviceId` 有个坑：方法前面 `Utils.OoooOo0(context, ...)` 确实生成过一个值
  存进缓存，但最后 put 进头的仍是空串。）要发派生假值做对照实验时设
  `PACE_DEVICE_HW_HEADERS=derived`。`DeviceId` 不受这个开关影响——它是设备锁。

## 下载与安装

### 预编译包（Windows x64 / Linux x64）

提供发布包后，可到 [GitHub Releases](https://github.com/IRmsk/pace-forge/releases) 选择对应系统的版本：

|---|---|

归档包包含可执行文件、`LICENSE`、本 README、`build-info.json` 和启动脚本：Windows 使用 `start-web.cmd`，Linux 使用 `start-web.sh`。预编译包不需要安装 Rust/Cargo。当前发布目标为 Windows x64 MSVC（静态 CRT）和 Linux x64 musl；具体兼容性以对应版本的 CI 构建结果为准。

升级前先看 [CHANGELOG.md](CHANGELOG.md)：标 `[行为变化]` 的版本会改变默认行为（例如自动规划不再被操场反推覆盖、计分跑围栏失败即停），只想要旧行为可以先不动。

Windows：解压 ZIP，在解压目录打开 PowerShell，运行：


也可以运行 `start-web.cmd`。终端窗口会保持打开；访问 `http://127.0.0.1:9999`，结束时在终端按 Ctrl+C。

Linux：解压归档，进入包含 `pace-forge` 的目录，运行：

```bash
pace-forge web
```

### 作为库

```rust
use pace_forge::track::{
    plan, sample_times, sample_by_time, simulate, inspect,
    Check, PlanRequest, SimParams, KinParams, SAMPLE_INTERVAL_SEC,
};

let planned = plan(&req, &mut rng)?;                                  // ① 规划
let xy: Vec<(f64, f64)> = planned.points.iter().map(|p| (p.lat, p.lon)).collect();

// ② 5 秒等时间轴（真机上报名就是 5 秒一点，别自己造 1~2 秒的间隔）
let times = sample_times(720, start_ms, SAMPLE_INTERVAL_SEC);

// ③ 按时间积分弧长：每个采样点落在「这一拍该走到的弧长」上。
//    打卡点要一起传进去，规划完会把最近的采样点吸附到打卡点的路径投影上，
//    否则点位离打卡点十几米，服务端判「没经过」。
let track = sample_by_time(
    &xy, &times, start_ms as u64, &KinParams::default(),
    0.9, 6.3, &[], &cps,
);

// ④ 合成步态/分桶
let pts: Vec<(f64, f64, i64)> = track.iter().map(|t| (t.lat, t.lon, t.time_ms)).collect();
let sim = simulate(&pts, &SimParams {
    total_distance_m: len as f64,
    total_sec: 720,
    start_ms,
    target_steps: None,
    seed,
    ..Default::default()
})?;

let report = inspect(&check);                                         // ⑤ 自检
if report.blocked() {
    eprintln!("{}", report.summary());
}
```

> 别用 `track::simulate::retime()`：那是「等距点位 + 按速度分配时间」的旧路径，
> 给出的时间轴是等距的，和真机 5 秒等时间采样对不上。现在只有历史测试还在用它。

## 协议要点

几个容易踩的坑，都是实测确认的：

**信封**：`{"d","h","k","p":"101","t":"0"}`。RSA-1024 加密 AES 密钥，AES-128-CBC 用**全零 IV**，密钥派生是三段自定义函数（`byte_hash` → `feistel_transform` → `final_mix`）。

**速度字段**（两个层级不同，别混）：记录级 `speed = 配速(分/公里) × 1000`（整数，用 `speedTop=2.0 / speedBottom=10.0` 反推确认）；点位级 `speed` **就是配速 min/km 浮点**（`5.08` 这种），和 `avgSpeed`(m/s) 满足 `speed × avgSpeed = 1000/60`。点位 `bdS` 是独立的低通速度，**不与 `speed` 同源**。

**点位接口**：`runec` 字段是额外一层信封，外层顺序 `k,p,d,h,t`（不是标准体的 `d,h,k,p,t`）；`sign = MD5(http版URL + 盐)`，注意是 **http://** 不是 https://；限流 5 分钟 3 次。

**OBS 上传**：`method` 参数是 `"Put"` 首字母大写，不是 `"PUT"`。

**静默窗口**：提交后 600 秒内不能再发跑步请求，否则判异常。

**提交体字段**（按 7.4.21 脱壳的 `UploadFormatEntity` 逐字段核过，47 个）：

- `segmentJson` 客户端算完反作弊后**清成空串**再发（`setSegmentJson` 最后一行
  `this.segmentJson = ""`），我们也发空串
- `more` 默认 `true`；`prizeName` 走 Gson `serializeNulls`，有键无值
- **顶层没有 `runAreaId`**，它只在 `fivePointJson` 那层 envelope
  （`PointJsonEntity`）里
- `useMobilityTools` 是客户端算出来的「是否用移动工具」标记，正常 0
- `appVersion` 默认 `7.4.21`（`PACE_APP_VERSION` 可覆盖）

**五点位 `isFixed` 默认全发 0**。7.4.21 的地图渲染按 `isFixed∈{1,2}` 分两套图标：

```java
// com.zjwh.map.gaode.Oooo000.setFivePoint
if ((isFixed != 1) && (isFixed != 2))
    icon = isPassed ? img_point_normal_pass : img_point_normal;
else
    icon = isPassed ? img_point_must_pass : img_point_must_normal;
```

实测：发真实的 `isFixed=1` 时，**即使 `isPass=true`**，App 详情页那个必经点也固定
画橙色（OBS 里五个点全 true 也照样橙）。全发 0 之后详情页 5 绿。代价是
`reasonList` 里「经过必经点位」显示 ✗，但 `complete=true`、`validDis` 全额、
`semesterValidDis` 也全额（实测 31201/31201 没扣）。

要发真实值做对照：`PACE_FORCE_NORMAL_POINT=0`。

**`isPass` 恒发 true**：它是 `entity/database/FivePoint` 的本地 Room 字段，由 App
在跑动中按 GPS 写库，服务端不认它（服务端自己从轨迹判「有没有经过」）。早先按
严格 10m 命中发 false，会让详情页画橙。

**点位判定阈值**：客户端用 **50 米**（`FivePointPlugin.OooOOOO` 里 `v2 <= 50.0`，
另有 60 米那档做「正在接近」提示）。我们用 10 米是**故意保守**——`position` 发的
是「首次经过的轨迹点下标」，而 planner 只在 15m 内吸附；按 50m 判命中会让 position
指向几十米外的点，App 拿这个下标核对反而更容易判没经过。

## 已知偏差

对着真机汇总值比出来的、暂时还没修的两处方向性差异（详见
[evidence 文档](evidence/real-device-app-summary.md)）：

- **极端慢点深度不够**：真机能出现 `364 min/km` 的点（5 秒走 23 厘米），我们最低
  到 `31'46"`。卡在 `track::MIN_SAMPLE_GAP_M = 0.5`——相邻采样点间距被钉在
  0.5 米，配速上限就被钳住了。
- **步态偏「小步高频」**：真机两条记录是 90~104 步/分 × 158~164cm，我们是
  157 步/分 × 110cm。乘积相同所以配速对得上，但真机那两个数其实是
  「距离 ÷ 步数 ÷ 时长」派生的（手机计步器少计），不是真实步态。

另外几处**改完但没真机验证**的（等能正常登录时验）：

- **跑法映射**：网页「跑法」只有两项——记分跑（`sportType=1`）和户外跑（`sportType=4`）。
  早先那张「`runMode=2/3` 就是自由跑」的表是错的，已按 neko 实测改成
  「`sportType` 决定跑法、`runMode` 只决定拉哪套策略」。
- **超长目标**：15km 这类目标生成不到（围栏周长限制，实测目标 15km → 实际 10.5km）。
- **日上限**：从 `runRuleModel.dayGoal` 自动读（实测某校 3000m），读不到退回 5000；`getHistoryConfig` 里的 `maleDayUpper=5000` 与实际结算不符，别信它。
- **月度抽检**：`creditscore/v70390/popup` 命中时要真人做支付宝信用分核验，
  自动化替不了，只做提醒。

## 登录失败排查

登录是最容易卡住的一步，绝大多数失败都能从**错误码**直接定位。先看服务端返回的 `error` 值（Web 界面会原样显示，CLI 会打在 stderr）：

### 10121 · 此账号已在其他设备登录

```
10121 登录失败，此账号已在其他设备登录，因账号保护机制，原状态未退出；
请过一小时后登录或原设备退出后再登录
```

服务端按 `device_id` 认设备。同一个账号每次登录必须用**同一个** device_id，否则它认为你在换手机，直接锁号一小时。

本项目按「手机号」做作用域，一个账号有且只有一套 device_id，存在数据根目录下的 `.pace-forge-device-id-<hash>`。会触发这个错误的情况：

- 之前用过别的同类工具，它给账号挂了另一个 device_id
- 手动删过数据根目录下的 `.pace-forge-device-id*` 文件
- 用同一个账号在手机 App 和本工具之间来回登录

**处理**：等满一小时再试。如果反复触发，去手机 App 里主动退出登录，让它清掉旧会话，再回来登录。

注意：**锁定期内每次重试都会重新计时**，越试越久。等就行，别刷。

### 需要过极验滑块

极验 v4 是本地求解（Canny 边缘 + NCC 匹配 + PoW），不需要打码平台。如果反复失败：

- 检查出口 IP。机房 / 公共代理的 IP 会被极验直接判风险，换成家宽
- 网络抖动导致 challenge 过期。重试即可
- 出口走了透明代理（Clash TUN 之类）时，`run.gxapp.iydsj.com` 的 TLS 指纹可能被改，直连或加规则绕开

### 连接失败 / Connect error

不是账号问题，是本机到 `run.gxapp.iydsj.com` 不通。先确认：

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://run.gxapp.iydsj.com/
```

通不了就是网络层的事（代理、DNS、防火墙），和本项目无关。

### 拉数据失败但登录成功

登录成功、后面某一步失败，通常是**接口限流**。打卡点接口限「前 5 分钟内最多 3 次」（错误码 `10603`），本项目带 5 分钟缓存，正常用不会碰到。如果手快连点，等 5 分钟。

把完整错误贴到 Issue 里，包括 `error=` 后面的数字和 message。只写「登录不进去」没法定位——`10121`（设备锁）、`10603`（限流）、密码错、极验失败，处理方式完全不同。
